Part one · Foundations

The ideas Spring is built on

Before any annotation makes sense, you need to understand the single problem Spring set out to solve and the trick it uses to solve it. Nothing here is Spring Boot yet. This is the bedrock.

Chapter 1What Spring is, and the problem it solves

Spring is a framework for building Java applications. That definition is true but useless, so let us start from the problem instead. Once you feel the problem, the framework stops being a pile of annotations and becomes an obvious solution.

The problem: objects creating other objects

Imagine a small application that saves orders. You write three classes: a controller that receives web requests, a service that applies your business rules, and a repository that writes to the database.

Plain Java, no framework 
class OrderRepository {
    void save(Order order) { /* write to database */ }
}

class OrderService {
    private OrderRepository repository = new OrderRepository();

    void placeOrder(Order order) {
        // business rules here
        repository.save(order);
    }
}

class OrderController {
    private OrderService service = new OrderService();

    void handleRequest(Order order) {
        service.placeOrder(order);
    }
}

This works. It also has four problems that grow worse every month the project lives.

One: every class is welded to a specific implementation. OrderService does not just use a repository, it uses exactly OrderRepository and no other. The day you need a version that writes to MongoDB instead of MySQL, you must edit OrderService — a class that has nothing to do with databases.

Two: you cannot test it in isolation. To test the business rules in OrderService, you need a real database running, because OrderService builds a real repository the moment it is created. A test that needs a database is slow and fragile.

Three: object creation spreads everywhere. new appears in dozens of files. If OrderRepository suddenly needs a connection pool passed into its constructor, every single place that wrote new OrderRepository() must change.

Four: you cannot share. Each class that says new OrderRepository() gets its own separate copy. If that repository holds an expensive database connection pool, you have now opened twenty pools where one would do.

In everyday terms

Think of a restaurant kitchen. In the code above, every chef who needs a knife walks out of the building, buys a knife, and brings it back. It works, but it is wasteful, it means every chef must know where the knife shop is, and if the shop changes its address, every chef must be retrained. A sensible kitchen has someone who stocks the knives and hands them to whoever needs one. That person is the Spring container.

The solution in one sentence

Spring's answer is: stop letting your classes create their own dependencies. Let them declare what they need, and let something else supply it. That something else is the Spring container. This idea is called Inversion of Control, and the mechanism is called Dependency Injection. Chapter 3 covers both in detail; for now just hold the shape of the idea.

The same classes, written the Spring way 
class OrderService {
    private final OrderRepository repository;

    // "I need a repository. I am not going to make one.
    //  Whoever creates me must hand one over."
    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}

Now OrderService can be tested with a fake repository, can be handed a MongoDB repository without any edit, and no longer contains the word new. That is the whole idea. Everything else in Spring is built on top of it.

What "the Spring Framework" actually contains

Spring grew from that one idea into a family of projects. You will meet these names constantly, so here is the map.

ProjectWhat it does for you
Spring CoreThe container. Creates objects, wires them together, manages their lifetimes. Everything else depends on this.
Spring MVCTurns HTTP requests into Java method calls and Java return values back into HTTP responses. This is how you build web APIs.
Spring DataRemoves most database code. You declare an interface describing what you want; Spring writes the query.
Spring SecurityLogin, passwords, tokens, roles, and who is allowed to call what.
Spring AOPLets you apply behaviour like logging or transactions around methods without editing those methods.

Where people go wrong

Beginners often think Spring Boot replaced Spring, the way a new phone replaces an old one. It did not. Spring Boot is Spring, plus sensible defaults and automatic setup. Every bean, every annotation, every piece of dependency injection you learn in Part One is still exactly what is happening inside a Spring Boot application. Learning the foundations is not optional history; it is a description of the machine you will be running.

Worth remembering

Spring exists so that your classes can say what they need instead of building it themselves. Every feature in the framework is a consequence of that one decision.

Chapter 2The Java you need before you begin

Spring is written in ordinary Java. If certain Java features feel shaky, Spring code will look like magic when it is not. This chapter is a quick, honest check of the five things that matter most. If you know them, skim. If any one is unfamiliar, spend twenty minutes here and the rest of the book gets easier.

Interfaces, and why Spring loves them

An interface is a contract: a list of method signatures with no bodies. A class that implements the interface must provide the bodies.

interface PaymentGateway {
    boolean charge(String cardNumber, double amount);
}

class StripeGateway implements PaymentGateway {
    public boolean charge(String cardNumber, double amount) {
        // real Stripe call
        return true;
    }
}

class FakeGateway implements PaymentGateway {
    public boolean charge(String cardNumber, double amount) {
        return true;   // always succeeds, useful in tests
    }
}

Because both classes implement the same interface, code written against PaymentGateway works with either one. That is the swap Spring performs for you. Whenever you see a Spring example where a field is typed as an interface, this is why.

Annotations, and what they really are

An annotation is a note attached to a class, method, field, or parameter. It changes nothing on its own. It is a label, and it only matters because some other program reads the label and reacts.

@Service              // <- this is a label
class OrderService { }

Writing @Service does not create anything. At startup, Spring scans your classes, finds the ones carrying that label, and builds them. The annotation is a sticky note; Spring is the person reading the sticky notes.

In everyday terms

An annotation is like writing "FRAGILE" on a box. The word does not make the box fragile and does not protect anything by itself. It works only because the delivery driver reads it and handles the box differently. Spring is the delivery driver.

You can define your own annotation, which makes it clear how simple they are:

@Retention(RetentionPolicy.RUNTIME)   // keep it available while the program runs
@Target(ElementType.METHOD)           // it may only be placed on methods
public @interface Timed { }

@Retention(RUNTIME) matters: without it the label is thrown away when the code compiles and Spring could never see it. Every Spring annotation is declared this way.

Generics

Generics let a class work with a type that is decided later. List<String> is a list that holds strings, checked at compile time.

interface Repository<T, ID> {
    T findById(ID id);
    void save(T entity);
}

interface UserRepository extends Repository<User, Long> { }

That second line is almost exactly how Spring Data works. You will write interface UserRepository extends JpaRepository<User, Long> and get twenty working methods for free. Knowing generics is what makes that line readable instead of mystifying.

Lambdas and functional interfaces

An interface with exactly one abstract method can be implemented with a short expression instead of a whole class.

// the long way
Runnable task = new Runnable() {
    public void run() { System.out.println("working"); }
};

// the same thing as a lambda
Runnable task = () -> System.out.println("working");

Spring Security configuration, WebClient calls, and modern Spring APIs are written almost entirely in this style, so lambdas are not optional.

Optional and streams

Optional<T> is a box that either holds a value or is empty. It exists so that "not found" is expressed in the type instead of by returning null and hoping the caller checks.

Optional<User> found = repository.findById(5L);

User user = found.orElseThrow(() -> new UserNotFoundException(5L));
String name = found.map(User::getName).orElse("unknown");
found.ifPresent(u -> System.out.println(u.getName()));

Spring Data repositories return Optional from findById, so you will use this on your first day.

Streams let you transform collections declaratively, which you will use constantly to convert database entities into response objects:

List<UserResponse> responses = users.stream()
        .filter(u -> u.isActive())
        .map(u -> new UserResponse(u.getId(), u.getName()))
        .toList();
Worth remembering

Annotations are inert labels. Interfaces are what make substitution possible. Generics are what make Spring Data's one-line repositories possible. Everything else Spring does is built from these ordinary Java parts.

Chapter 3Inversion of Control and Dependency Injection

These two terms are used interchangeably in casual conversation, which causes confusion, so let us separate them clearly and then never worry about it again.

Inversion of Control (IoC) is the principle. Normally your code is in control: it decides when to create objects and which ones. Inverted control means the framework is in control: it creates the objects and calls your code at the right moment. The control has been turned upside down, hence "inversion."

Dependency Injection (DI) is the specific technique Spring uses to achieve that principle. Your object declares what it needs and the container hands those things over — it injects them.

In everyday terms

Inversion of Control is the rule "you don't call us, we'll call you." Dependency Injection is the practical way it happens: instead of you going to fetch your tools, someone puts the tools in your hands before you start work. IoC is the policy; DI is the delivery method.

A dependency, defined

If class A cannot do its job without class B, then B is a dependency of A. OrderService cannot save an order without OrderRepository, so the repository is a dependency of the service. That is the entire definition. There is nothing more subtle hiding in the word.

The three ways to inject

1. Constructor injection — use this one

@Service
public class OrderService {

    private final OrderRepository repository;
    private final EmailSender emailSender;

    public OrderService(OrderRepository repository, EmailSender emailSender) {
        this.repository = repository;
        this.emailSender = emailSender;
    }
}

Spring sees the constructor, works out what types it needs, finds matching beans, and calls the constructor with them. You do not need @Autowired on the constructor when the class has only one constructor — Spring assumes it.

Why this is the right default:

  • The fields can be final, so nothing can replace them later. The object cannot exist in a half-built state.
  • The dependencies are visible in the signature. Anyone reading the class sees immediately what it needs.
  • In a unit test you just call new OrderService(fakeRepo, fakeMailer) with no Spring involved at all.
  • If the constructor grows to eight parameters, that ugliness is a useful signal that the class is doing too much. Field injection hides that signal.

2. Setter injection — for genuinely optional dependencies

@Service
public class ReportService {

    private ExportFormatter formatter;

    @Autowired(required = false)
    public void setFormatter(ExportFormatter formatter) {
        this.formatter = formatter;
    }
}

Use it when the dependency really is optional or must be swappable after construction. That is rare.

3. Field injection — avoid it

@Service
public class OrderService {
    @Autowired
    private OrderRepository repository;   // works, but don't
}

It is the shortest to type, which is why tutorials use it, and it is the worst of the three. The field cannot be final. You cannot construct the object in a test without reflection. The class can be compiled and instantiated while missing a dependency, failing only at runtime with a NullPointerException. Modern IntelliJ actively warns against it.

Where people go wrong

Two classes that each need the other — a circular dependency — will fail at startup with constructor injection, and people "fix" it by switching to field injection. That is not a fix; it is hiding a design problem. A circle means your responsibilities are drawn in the wrong place. Extract the shared logic into a third class, or use an event, as shown in Chapter 7.

Seeing it work end to end

public interface MessageSender {
    void send(String to, String text);
}

@Component
public class EmailSender implements MessageSender {
    public void send(String to, String text) {
        System.out.println("Email to " + to + ": " + text);
    }
}

@Service
public class NotificationService {
    private final MessageSender sender;

    public NotificationService(MessageSender sender) {   // asks for the interface
        this.sender = sender;
    }

    public void notifyUser(String email) {
        sender.send(email, "Your order has shipped.");
    }
}

NotificationService never names EmailSender. It asks for the contract. Tomorrow you write SmsSender implements MessageSender, mark it as the one to use, and the notification service is untouched. That flexibility is the practical payoff of all this indirection.

Worth remembering

Declare dependencies in the constructor, type them as interfaces where a swap is plausible, and never write new for something the container could give you.

Chapter 4Beans and the Spring container

A bean is simply an object that Spring created and is looking after. That is all. Not a special kind of class, not an interface you implement — just a normal Java object whose creation you handed over to the framework.

The container (its formal name is the ApplicationContext) is the thing holding all those objects. At startup it reads your configuration, decides what to build, builds it in the right order, injects everything, and keeps a map from type and name to instance.

In everyday terms

The container is a warehouse and beans are the stock inside it. When a class asks for an OrderRepository, the container checks the shelves and hands one over. Your code never visits the factory.

Where beans come from

There are exactly two ways an object becomes a bean, and every Spring application uses both.

Way one: a stereotype annotation plus component scanning

You put an annotation on your own class and Spring finds it while scanning packages.

@Component   // the generic one
public class PriceCalculator { }

@Service     // for business logic
public class OrderService { }

@Repository  // for database access
public class OrderRepository { }

@Controller  // for web request handling
public class OrderController { }

Technically @Service, @Repository, and @Controller are all @Component underneath. They exist so that a reader can tell a class's role at a glance, and so that Spring can add role-specific behaviour. @Repository, for example, translates vendor-specific database exceptions into Spring's own consistent exception types. So the distinction is not purely decorative, but the difference is small.

Way two: an @Bean method inside a configuration class

You use this when the class is not yours to annotate — a library class, for instance — or when creating it takes real logic.

@Configuration
public class AppConfig {

    @Bean
    public ObjectMapper objectMapper() {
        ObjectMapper mapper = new ObjectMapper();
        mapper.setSerializationInclusion(Include.NON_NULL);
        return mapper;
    }

    @Bean
    public RestClient restClient(ObjectMapper mapper) {   // dependencies as parameters
        return RestClient.builder()
                .baseUrl("https://api.example.com")
                .build();
    }
}

The method name becomes the bean's name. The return value becomes the bean. Parameters are themselves injected — Spring resolves mapper from the bean it just made.

Where people go wrong

You cannot put @Component on a class that lives in someone else's jar. If you need a bean of a third-party type, an @Bean method is the only option. Learners often get stuck here trying to annotate a class they cannot edit.

Component scanning: how Spring finds your classes

Spring does not search your whole disk. It scans a set of packages you nominate. In Spring Boot, the class annotated with @SpringBootApplication nominates its own package and every package beneath it.

com.example.shop
├── ShopApplication.java        <- @SpringBootApplication lives here
├── controller/                 <- scanned
├── service/                    <- scanned
└── repository/                 <- scanned

com.other.tools                 <- NOT scanned
Where people go wrong

This causes more "why is my bean not found?" questions than anything else. If a class sits outside the main class's package tree, Spring never sees it, no matter how many annotations it carries. Keep the application class at the root of your package structure. If you truly must scan elsewhere, add @ComponentScan(basePackages = {"com.example.shop", "com.other.tools"}).

Bean names, and getting hold of the container

Every bean has a name. For a scanned class it defaults to the class name with a lowercase first letter: OrderService becomes orderService. For an @Bean method it is the method name. You can override it: @Component("calculator").

You almost never need to touch the container yourself, but seeing it demystifies things:

@SpringBootApplication
public class ShopApplication {
    public static void main(String[] args) {
        ApplicationContext context = SpringApplication.run(ShopApplication.class, args);

        OrderService service = context.getBean(OrderService.class);
        System.out.println("Total beans: " + context.getBeanDefinitionCount());
    }
}

Run that and you will see several hundred beans. Most were created for you by auto-configuration, which Chapter 11 explains.

Worth remembering

A bean is just an object Spring made. It comes either from a scanned @Component in your own code, or from an @Bean method when the class is not yours.

Chapter 5Wiring: choosing between candidates

Injection is easy when exactly one bean matches the requested type. Real applications are not so tidy, and this chapter covers what happens when zero or several match.

The ambiguity problem

public interface PaymentGateway { }

@Component class StripeGateway implements PaymentGateway { }
@Component class PaypalGateway implements PaymentGateway { }

@Service
public class CheckoutService {
    public CheckoutService(PaymentGateway gateway) { ... }   // which one?
}

Spring cannot guess, so it refuses to start and reports NoUniqueBeanDefinitionException. This is a feature: a silent wrong guess would be far worse than a loud failure. You resolve it in one of three ways.

@Primary — declare a default

@Component
@Primary
class StripeGateway implements PaymentGateway { }

Now anyone asking for a PaymentGateway without being more specific gets Stripe. Use this when one implementation is genuinely the normal choice.

@Qualifier — name the one you want

@Component("paypal")
class PaypalGateway implements PaymentGateway { }

@Service
public class CheckoutService {
    public CheckoutService(@Qualifier("paypal") PaymentGateway gateway) { ... }
}

A custom qualifier annotation — the tidiest option

String names are typo-prone. You can make a qualifier that the compiler checks:

@Qualifier
@Retention(RetentionPolicy.RUNTIME)
public @interface Paypal { }

@Component @Paypal
class PaypalGateway implements PaymentGateway { }

public CheckoutService(@Paypal PaymentGateway gateway) { ... }

Injecting every implementation at once

Sometimes you want all of them, not one. Ask for a List or a Map:

@Service
public class ValidationRunner {

    private final List<Validator> validators;         // every Validator bean
    private final Map<String, PaymentGateway> gateways; // bean name -> bean

    public ValidationRunner(List<Validator> validators,
                            Map<String, PaymentGateway> gateways) {
        this.validators = validators;
        this.gateways = gateways;
    }

    public void validate(Order order) {
        validators.forEach(v -> v.check(order));
    }
}

This is a genuinely powerful pattern. To add a new validation rule you write one new class with @Component and change nothing else — the list grows by itself. Control the order with @Order(1), @Order(2) on the implementations.

Optional dependencies

// Option A: Spring will pass null rather than fail
@Autowired(required = false)
private MetricsCollector metrics;

// Option B: clearer, using Optional in the constructor
public OrderService(Optional<MetricsCollector> metrics) { ... }

// Option C: a default when nothing else defines one
@Bean
@ConditionalOnMissingBean
public MetricsCollector noOpMetrics() { return new NoOpMetrics(); }

Reading the failure messages

MessageWhat it meansFix

Worth remembering

One match, Spring injects it. Several matches, Spring stops and asks you to choose with @Primary or @Qualifier. Ask for a List when you want all of them.

Chapter 6Bean scopes: how many copies exist

A scope answers one question: when several parts of the application ask for this bean, do they get the same object or different objects?

Singleton — the default

One instance for the whole application. Created once at startup, shared by everyone. Unless you say otherwise, every bean you write is a singleton.

@Service
public class OrderService { }          // singleton

@Service
@Scope("singleton")                    // same thing, written out
public class OrderService { }

This is efficient, but it carries an obligation that trips people up constantly.

Where people go wrong

A singleton is shared by every request, and web requests run on many threads at once. So a singleton bean must not keep changeable state in a field. This is wrong:

@Service
public class BadCounter {
    private int count = 0;             // shared across all users!
    public void handle() { count++; }  // two threads here corrupts the value
}

Keep state in local variables inside methods, or in the database. Fields on a singleton should hold dependencies and configuration only — things that are set once and never change.

Prototype — a fresh object every time

@Component
@Scope("prototype")
public class ShoppingCart { }

Every injection point and every getBean call produces a brand new instance. Use it for objects that genuinely hold per-use state.

Where people go wrong

Injecting a prototype into a singleton does not give you a new one each time you use it. The singleton is built once, so it receives one prototype instance and holds it forever. If you need a genuinely fresh instance per call, inject an ObjectProvider and ask it each time:

@Service
public class CartService {
    private final ObjectProvider<ShoppingCart> carts;

    public CartService(ObjectProvider<ShoppingCart> carts) { this.carts = carts; }

    public ShoppingCart newCart() { return carts.getObject(); }  // fresh each call
}

The web scopes

These exist only in a web application.

ScopeOne instance per…Typical use
requestHTTP requestData collected while handling one request, such as a correlation id
sessionUser sessionA logged-in user's preferences or wizard progress
applicationServlet contextRare; similar to singleton
websocketWebSocket sessionPer-connection state in chat-style apps
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class RequestContext {
    private String correlationId;
    // getters and setters
}

The proxyMode matters. A singleton service lives longer than any request, so Spring cannot hand it a real request-scoped object at startup — there is no request yet. Instead it injects a lightweight stand-in that looks up the correct instance for whichever request is currently running. Without this setting, injection into a singleton fails.

Worth remembering

Default to singleton and keep those beans stateless. Reach for another scope only when an object truly must hold per-user or per-request data.

Chapter 7Bean lifecycle and application events

Between "Spring decides to create this bean" and "Spring throws it away," several things happen in a fixed order. You rarely need all of them, but two hooks are genuinely useful and one common problem is solved by events.

The order of events at creation

  1. Spring reads the bean definition — the class, its scope, its dependencies.
  2. The constructor runs, with dependencies passed in.
  3. Fields and setters marked @Autowired are filled.
  4. @PostConstruct methods run. All dependencies are now guaranteed present.
  5. Any BeanPostProcessor wraps the bean — this is where proxies for transactions, caching, and security are added.
  6. The bean is ready and handed out.
  7. At shutdown, @PreDestroy methods run.

The two hooks worth knowing

@Service
public class CacheWarmer {

    private final ProductRepository repository;
    private Map<Long, Product> cache;

    public CacheWarmer(ProductRepository repository) {
        this.repository = repository;
        // Do NOT use the repository here for real work; the object
        // is still being assembled and proxies are not applied yet.
    }

    @PostConstruct
    public void loadCache() {
        cache = repository.findAll().stream()
                .collect(toMap(Product::getId, p -> p));
    }

    @PreDestroy
    public void cleanUp() {
        cache.clear();
    }
}

@PostConstruct is for setup that needs dependencies. @PreDestroy is for releasing things Spring does not know about, such as a file handle or a thread you started yourself.

Where people go wrong

Doing real work inside a constructor. At that moment the object is not yet wrapped in its proxies, so a @Transactional or @Cacheable method called from the constructor will quietly run without a transaction or cache. Constructors should only assign fields. Anything else belongs in @PostConstruct.

Running code once at startup

If you want something to happen after the whole application has finished starting, not just one bean, use a runner:

@Component
public class SeedData implements CommandLineRunner {
    private final UserRepository repository;

    public SeedData(UserRepository repository) { this.repository = repository; }

    @Override
    public void run(String... args) {
        if (repository.count() == 0) {
            repository.save(new User("admin", "admin@example.com"));
        }
    }
}

Application events: decoupling without dependencies

Suppose placing an order should send an email, update a metric, and notify a warehouse. Injecting three services into OrderService makes it depend on all three. Events let you invert that.

// 1. The event — a plain record describing what happened
public record OrderPlacedEvent(Long orderId, String customerEmail) { }

// 2. The publisher
@Service
public class OrderService {
    private final ApplicationEventPublisher events;

    public OrderService(ApplicationEventPublisher events) { this.events = events; }

    public void placeOrder(Order order) {
        // save the order...
        events.publishEvent(new OrderPlacedEvent(order.getId(), order.getEmail()));
    }
}

// 3. Any number of listeners, each unknown to the publisher
@Component
public class EmailOnOrder {
    @EventListener
    public void on(OrderPlacedEvent event) {
        // send the confirmation email
    }
}

By default listeners run on the same thread, inside the same transaction, before placeOrder returns. Add @Async to run one in the background, and prefer @TransactionalEventListener when the listener should only fire after the database commit succeeds:

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderPlacedEvent event) { /* email only if the save worked */ }
In everyday terms

Direct method calls are phone calls: you must know the number, and you wait for an answer. Events are a notice on a board: you post what happened and anyone who cares reads it. The poster does not need to know who is reading.

Worth remembering

Constructors assign, @PostConstruct initialises. When one action should trigger several unrelated reactions, publish an event instead of injecting every reactor.

Chapter 8Aspect-Oriented Programming

Some concerns do not belong to any single class but must happen in many of them: logging, timing, security checks, transactions, retries. Copying that code into fifty methods is miserable to write and worse to change. AOP is the mechanism for writing it once and applying it from the outside.

In everyday terms

Think of a building where every room needs a smoke detector. You would not rebuild each room with detection logic in its walls. You install detectors from outside, into rooms that do not know they are being monitored. AOP does this to methods.

The vocabulary, translated

TermPlain meaning
AspectThe class holding your cross-cutting code
AdviceThe code itself, and when it runs (before, after, around)
Join pointA place where advice could be applied. In Spring, always a method call
PointcutThe expression that selects which methods to apply it to
TargetThe real object being wrapped
ProxyThe wrapper Spring puts around the target so advice can run

A working example: timing every service method

Add the starter first:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
</dependency>
@Aspect
@Component
public class TimingAspect {

    private static final Logger log = LoggerFactory.getLogger(TimingAspect.class);

    @Around("execution(* com.example.shop.service..*(..))")
    public Object time(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            return joinPoint.proceed();          // run the real method
        } finally {
            long taken = System.currentTimeMillis() - start;
            log.info("{} took {} ms", joinPoint.getSignature().getName(), taken);
        }
    }
}

Not one service class changes. Every method in that package is now timed.

Reading a pointcut expression

execution(* com.example.shop.service..*(..))
          │  │                        │  │
          │  │                        │  └── any parameters
          │  │                        └───── any method name
          │  └────────────────────────────── that package and sub-packages
          └───────────────────────────────── any return type

Other useful forms:

execution(public * *(..))                     // any public method
execution(* *..OrderService.place*(..))       // methods starting with "place"
@annotation(com.example.Timed)                // methods carrying @Timed
within(com.example.shop.service.*)            // any method in that package
bean(*Repository)                             // beans whose name ends in Repository

The five kinds of advice

@Before("...")          // runs first; cannot stop the method
@AfterReturning("...")  // runs only if the method returned normally
@AfterThrowing("...")   // runs only if it threw
@After("...")           // runs either way, like a finally block
@Around("...")          // wraps completely; can change arguments, the
                        // return value, or skip the method entirely

An annotation-driven aspect

Targeting by package is blunt. Targeting by annotation is precise:

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface AuditLog { String value(); }

@Aspect @Component
public class AuditAspect {

    @AfterReturning("@annotation(auditLog)")
    public void record(JoinPoint joinPoint, AuditLog auditLog) {
        log.info("AUDIT {} by {}", auditLog.value(), currentUser());
    }
}

// usage
@AuditLog("delete-customer")
public void deleteCustomer(Long id) { ... }

The limitation you must know about

Where people go wrong

Spring AOP works by wrapping your bean in a proxy. Calls that arrive from outside go through the proxy and get the advice. A call from one method of the class to another method of the same class does not go through the proxy, so the advice is skipped.

@Service
public class ReportService {

    public void generateAll() {
        generateOne();      // @Timed is IGNORED — internal call
    }

    @Timed
    public void generateOne() { ... }
}

The same trap applies to @Transactional, @Cacheable, @Async and @PreAuthorize, because all of them use this same proxy mechanism. It is probably the single most common source of "why is my annotation doing nothing?" The fix is to move the annotated method into a different bean and inject it. Also note that proxies only intercept public methods — advice on a private method never runs.

Worth remembering

AOP wraps beans in proxies so that behaviour can be added without editing the class. Because it is a wrapper, a method calling another method inside the same class bypasses it entirely.

Chapter 9Configuration and external values

Hard-coding a database password into a Java file means recompiling to change it and leaking a secret into version control. Spring's answer is to keep such values outside the code and pull them in.

Java configuration classes

@Configuration
public class AppConfig {

    @Bean
    public TaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(16);
        executor.initialize();
        return executor;
    }
}

@Configuration does something subtle worth understanding. Spring proxies the class so that calling one @Bean method from another returns the existing singleton rather than creating a second object:

@Configuration
public class Config {
    @Bean public A a() { return new A(b()); }
    @Bean public B b() { return new B(); }   // b() called twice, ONE B created
}

If you write @Configuration(proxyBeanMethods = false) this protection is gone and you get two instances. The default is safe; leave it alone unless you know why you are changing it.

Reading a single value with @Value

application.properties

app.max-items=50
app.feature.dark-mode=true
app.admins=alice@example.com,bob@example.com
@Service

    @Value("${app.name}")

    @Value("${app.max-items}")

}

Grouping related values with @ConfigurationProperties

Once you have more than three or four related settings, @Value becomes noise. Bind a whole group into one object instead.

application.yml

  max-items: 50
  mail:
    host: smtp.example.com
    port: 587
    from: no-reply@example.com

        String name,
        int maxItems,
        Mail mail
) {
    public record Mail(String host, int port, String from) { }
}

@SpringBootApplication

public class ShopApplication { }
@Service
public class MailService {

    public MailService(AppProperties props) { this.props = props; }

        connect(props.mail().host(), props.mail().port());

}

Notice max-items in the file becomes maxItems in Java. Spring handles that translation, and also accepts MAX_ITEMS from an environment variable, which is how you will configure production.

You can validate the values at startup, so a bad configuration fails immediately rather than at 3am:

@ConfigurationProperties(prefix = "app")
@Validated
public record AppProperties(
        @NotBlank String name,
        @Min(1) @Max(1000) int maxItems
) { }

Where values come from, and who wins

Spring reads from many sources. Later entries override earlier ones:

  1. Defaults set in code
  2. application.properties or application.yml inside the jar
  3. application-{profile}.properties for the active profile
  4. A properties file sitting next to the jar on disk
  5. Operating system environment variables
  6. Java system properties (-Dapp.name=...)
  7. Command line arguments (--app.name=...)

This ordering is what lets one jar run unchanged in every environment: the same build, different environment variables.

Spring Expression Language, briefly

SpEL lets an expression appear where a value is expected. You will see it mostly in security rules and cache keys.

@Value("#{2 * 60 * 1000}")          long twoMinutes;
@Value("#{systemProperties['user.region']}") String region;
@Value("#{appProperties.maxItems > 10 ? 'large' : 'small'}") String size;

@PreAuthorize("#username == authentication.name")
public User load(String username) { ... }

${...} reads a property. #{...} evaluates an expression. Mixing the two up is a common small error.

Worth remembering

Single value, use @Value. A group of related settings, use @ConfigurationProperties with a record. Never put a secret in a Java file.

Part two · Spring Boot

From framework to running application

Spring gave us the container. Spring Boot removes the setup work that used to sit between a fresh project and a running server, and it does so with a mechanism you can inspect and override.

Chapter 10What Spring Boot actually does

Before Boot, starting a Spring web project meant choosing compatible versions of a dozen libraries, writing several XML files, configuring a servlet dispatcher, and deploying a WAR file into a separately installed Tomcat. A first "hello world" could take a day. Spring Boot reduced that to minutes with three ideas.

Idea one: starters

A starter is a dependency that pulls in a coherent set of other dependencies at versions known to work together. You ask for a capability, not a list of jars.

Idea two: auto-configuration

This is the part that feels like magic, so let us take the magic apart. Auto-configuration is a set of conditional @Bean methods that Spring Boot ships, each guarded by a condition. At startup Boot evaluates every condition and creates only the beans whose conditions pass.

// A simplified version of what Boot itself contains
@AutoConfiguration
@ConditionalOnClass(DataSource.class)              // only if JDBC is on the classpath
@ConditionalOnMissingBean(DataSource.class)        // only if you didn't define one
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    public DataSource dataSource(DataSourceProperties properties) {
        return properties.initializeDataSourceBuilder().build();
    }
}

Read those two conditions again, because together they explain the entire behaviour of Spring Boot:

  • "If the class is present" — adding a jar to your build is how you switch a feature on. Put the PostgreSQL driver on the classpath and Boot configures a PostgreSQL connection. Remove it and that configuration silently stops applying.
  • "If you have not defined one yourself" — the moment you declare your own DataSource bean, Boot's version steps aside. You are never locked in. Auto-configuration is a set of defaults, not a cage.

The common conditions are worth recognising:

@ConditionalOnClass          // a class is on the classpath
@ConditionalOnMissingClass   // it is not
@ConditionalOnBean           // some other bean already exists
@ConditionalOnMissingBean    // it does not — your definition wins
@ConditionalOnProperty       // a property has a given value
@ConditionalOnWebApplication // this is a web app
@ConditionalOnExpression     // an arbitrary SpEL expression is true

Seeing exactly what was auto-configured

Add this to application.properties and restart:

debug=true

You get a report listing every auto-configuration class, split into "Positive matches" (applied, with the reason) and "Negative matches" (skipped, with the reason). When something unexpected happens, this report usually contains the answer. It is the single best tool for replacing belief in magic with knowledge.

Idea three: the embedded server

Your application no longer gets deployed into a server. The server is a library inside your application. main() starts Tomcat on port 8080 and you ship one self-contained jar.

java -jar shop-0.0.1-SNAPSHOT.jar

This is what makes containerised and cloud deployment straightforward: the artefact is a normal process, not something requiring a pre-installed application server.

Old Spring was a kit of parts with a manual. Spring Boot is the same parts, pre-assembled the way most people want them, with every screw still reachable. You are not prevented from changing anything; you simply do not have to start from bare metal.

Chapter 13Logging

Logging is how you find out what a running system did. Spring Boot includes SLF4J as the API and Logback as the implementation, already configured, so you only need to use it well.

Writing a log line

@Service
public class OrderService {

    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void placeOrder(Order order) {
        log.debug("Placing order for customer {}", order.getCustomerId());
        try {
            // ...
            log.info("Order {} placed successfully", order.getId());
        } catch (PaymentException e) {
            log.error("Payment failed for order {}", order.getId(), e);
            throw e;
        }
    }
}

With Lombok you can replace the first line with @Slf4j on the class.

Where people go wrong

Building the message with string concatenation:

log.debug("Order " + order.getId() + " total " + order.getTotal());   // wrong
log.debug("Order {} total {}", order.getId(), order.getTotal());       // right

The first version builds the string every time even when debug logging is switched off. The second only formats if the line will actually be written. In a hot method called thousands of times per second, the difference is real.

Also note the exception goes last, with no placeholder: log.error("Failed for {}", id, e). Putting it inside the format string loses the stack trace.

In a busy system, lines from different requests interleave. MDC attaches a value to the current thread so every line from one request carries the same identifier:

@Component
public class RequestIdFilter extends OncePerRequestFilter {

    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ... {
        MDC.put("requestId", UUID.randomUUID().toString().substring(0, 8));
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.clear();      // essential: threads are reused
        }
    }
}

Part three · Building web APIs

Turning HTTP into method calls

This is the part you will use every working day: mapping URLs to methods, shaping what goes in and out, validating input, and failing gracefully.

Chapter 14How a request travels through Spring

Understanding this path once means you will know where to look when something misbehaves, instead of guessing.

The journey, step by step

  1. A browser or client sends GET /api/products/5 to port 8080.
  2. The embedded Tomcat accepts the connection and hands the request to a chain of filters. Security lives here, which is why security runs before your controller.
  3. The request reaches the DispatcherServlet, Spring's single front door for every request.
  4. The dispatcher asks a handler mapping which method matches that URL and HTTP verb. The answer is a method on one of your controllers.
  5. Interceptors registered for that path run their preHandle methods.
  6. Argument resolvers build the method's parameters: read the path variable 5, parse the JSON body into an object, pull a header.
  7. Your method runs.
  8. A message converter turns the returned object into JSON. For Java objects this is Jackson.
  9. Interceptors' postHandle and afterCompletion run, filters unwind, and the response goes back down the wire.

If an exception is thrown anywhere in steps 6 to 8, the dispatcher looks for an exception handler instead — the subject of Chapter 18.

In everyday terms

The DispatcherServlet is a receptionist. Every visitor comes to one desk. The receptionist checks the directory for who handles this kind of visitor, prepares whatever that person needs, sends the visitor through, and then packages the reply for the journey out.

Filters versus interceptors

Both intercept requests, and beginners confuse them.

public class TimingInterceptor implements HandlerInterceptor {

    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute("start", System.currentTimeMillis());
        return true;              // false would stop the request here
    }

    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        long ms = System.currentTimeMillis() - (long) req.getAttribute("start");
        log.info("{} {} -> {} in {}ms", req.getMethod(), req.getRequestURI(), res.getStatus(), ms);
    }
}

Chapter 16DTOs and the layered architecture

This chapter is about discipline rather than syntax, and it separates code that survives from code that rots.

Why you should not return entities from controllers

An entity is a database row expressed as an object. A response is a contract with a client. Letting one class serve both roles causes four concrete problems.

@Entity
public class User {
    @Id private Long id;
    private String email;
    private String passwordHash;          // 1. leaked to every caller
    @OneToMany private List<Order> orders; // 2. lazy loading blows up during JSON writing
}
  1. Exposure. Every field goes out, including ones that must never leave the server.
  2. Lazy loading failures. Jackson touches the orders collection after the transaction has closed, producing LazyInitializationException, or silently issuing dozens of extra queries.
  3. Accidental API changes. Renaming a database column renames a JSON field and breaks every client.
  4. Infinite recursion. If Order also points back to User, Jackson loops forever.

The shape of a clean flow

Client
  │  JSON in
  ▼

The "fat controller": a controller that injects the repository directly and holds the logic, leaving the service as an empty pass-through. It works for a week. Writing your own constraint

When a rule is specific to your domain, make it an annotation so it reads like the built-in ones.

@Documented
@Constraint(validatedBy = UniqueEmailValidator.class)
@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface UniqueEmail {
    String message() default "That email is already registered";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

@Component
public class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {

    private final UserRepository repository;
    public UniqueEmailValidator(UserRepository repository) { this.repository = repository; }

    @Override
    public boolean isValid(String email, ConstraintValidatorContext context) {
        return email == null || !repository.existsByEmail(email);
    }
}

Validators are beans, so they can inject repositories and services.

Where people go wrong

Two mistakes recur. First, forgetting @Valid — the annotations are then decoration and nothing is checked. Second, treating annotation validation as sufficient. It checks the shape of the data. Rules that depend on other data ("this discount code has not expired", "the account has enough balance") belong in the service, where they can throw a meaningful domain exception.

Worth remembering

Constraint annotations describe the shape of valid input and require @Valid to run. Business rules that need context live in the service layer.

Chapter 18Exception handling

Without deliberate handling, any exception becomes a 500 with a stack trace — useless to the client and a security risk. The goal is one place that turns every failure into a consistent, honest response.

Domain exceptions

Create exceptions that describe what went wrong in your domain, not in your plumbing.

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String resource, Object id) {
        super(resource + " with id " + id + " was not found");
    }
}

public class EmailAlreadyUsedException extends RuntimeException {
    public EmailAlreadyUsedException(String email) {
        super("Email " + email + " is already registered");
    }
}

public class InsufficientStockException extends RuntimeException {
    private final int available;
    public InsufficientStockException(int available) {
        super("Only " + available + " items left");

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(
            ResourceNotFoundException ex, HttpServletRequest request) {
        return build(HttpStatus.NOT_FOUND, ex.getMessage(), request, null);
    }

    @ExceptionHandler(EmailAlreadyUsedException.class)
    public ResponseEntity<ErrorResponse> handleConflict(
            EmailAlreadyUsedException ex, HttpServletRequest request) {
        return build(HttpStatus.CONFLICT, ex.getMessage(), request, null);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(
            MethodArgumentNotValidException ex, HttpServletRequest request) {

        Map<String, String> fields = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors()
          .forEach(e -> fields.put(e.getField(), e.getDefaultMessage()));

        return build(HttpStatus.BAD_REQUEST, "Validation failed", request, fields);
    }

    @ExceptionHandler(Exception.class)          // the safety net
    public ResponseEntity<ErrorResponse> handleEverythingElse(
            Exception ex, HttpServletRequest request) {
        log.error("Unhandled exception on {}", request.getRequestURI(), ex);
        return build(HttpStatus.INTERNAL_SERVER_ERROR,
                     "Something went wrong. Please try again.", request, null);
    }

    private ResponseEntity<ErrorResponse> build(HttpStatus status, String message,
                                               HttpServletRequest request,
                                               Map<String, String> fields) {
        ErrorResponse body = new ErrorResponse(
                LocalDateTime.now(), status.value(), status.getReasonPhrase(),
                message, request.getRequestURI(), fields);
        return ResponseEntity.status(status).body(body);
    }
}

Where people go wrong

Returning ex.getMessage() from the catch-all handler. That message may contain SQL fragments, table names, file paths, or internal hostnames — free reconnaissance for an attacker. Log the detail for yourself; return something generic to the client. This is the single most common security mistake in exception handling.

The shortcut, and the ProblemDetail standard

Worth remembering

One @RestControllerAdvice for the whole application, a consistent body shape, honest status codes, and never leak internal details in the message.

Timeouts, which are not optional

Where people go wrong

Calling an external service with no timeout. If that service hangs, your threads pile up waiting, and an outage in someone else's system becomes an outage in yours. Always set connect and read timeouts.

Use RestClient for new blocking code and WebClient when you need concurrency. Always set timeouts, and translate remote failures into your own exceptions at the boundary.

Working with a database

Most real applications are mostly database work. This part explains the layers between your objects and your tables, then shows how Spring Data removes nearly all the code.

Chapter 20JDBC, JPA, Hibernate, Spring Data

Four names appear constantly and people rarely explain how they relate. Here they are, from the bottom up.

JDBC — the foundation

The standard Java API for talking to a database. You write SQL as strings, run it, and read results row by row. Powerful, and extremely verbose.

String sql = "SELECT id, name FROM users WHERE id = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setLong(1, id);
    ResultSet rs = ps.executeQuery();
    if (rs.next()) {
        User user = new User();
        user.setId(rs.getLong("id"));
        user.setName(rs.getString("name"));
        return user;
    }
}

JPA — a specification, not a library

The Jakarta Persistence API defines how Java objects map to database tables, and the annotations for expressing it: @Entity, @Id, @Column, @OneToMany. JPA itself is only a set of interfaces and rules. You cannot run JPA; you run an implementation of it.

Hibernate — the implementation

The most widely used JPA implementation, and the one Spring Boot includes by default. Hibernate generates the SQL, tracks which objects have changed, manages caching, and handles lazy loading. When something surprising happens with your data, Hibernate is usually the thing doing it.

Spring Data JPA — the convenience layer

Sits on top of JPA and removes the remaining boilerplate. You declare an interface; Spring generates the implementation at startup.

public interface UserRepository extends JpaRepository<User, Long> { }
// save, findById, findAll, delete, count and more, all working, with no code
In everyday terms

JDBC is speaking the database's language yourself, word by word. JPA is the agreed grammar for translation between objects and tables. Hibernate is the translator who actually does the work. Spring Data is the assistant who calls the translator for you so you only have to say what you want.

ORM, and the bargain it offers

Object-Relational Mapping means working with objects and letting the tool produce SQL. You gain a great deal of speed and lose some visibility. The way to keep the gain without the pain is to stay aware of the SQL being produced — switch it on while developing:

spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
logging.level.org.hibernate.orm.jdbc.bind=TRACE

Where people go wrong

spring.jpa.hibernate.ddl-auto deserves real caution:

  • create-drop — rebuild the schema at startup, delete at shutdown. Fine for local work and tests.
  • update — try to alter the schema to match your entities. Convenient in development, dangerous in production: it never deletes, it makes silent changes, and it cannot be reviewed.
  • validate — check that the schema matches and fail if not. This is the correct production setting.
  • none — do nothing.

In production, use validate and manage schema changes with Flyway (Chapter 26).

Worth remembering

JPA is the rulebook, Hibernate does the work, Spring Data writes your repository code. Keep SQL logging on while you learn so the abstraction stays transparent.

equals and hashCode on entities

Where people go wrong

Letting Lombok's @Data or the IDE generate equals from all fields. Two problems follow. A new entity has a null id, so two unsaved objects compare equal. And an entity placed in a HashSet before saving changes its hash code once the id is assigned, so it becomes unfindable in the set it is already in.

The safe pattern:

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User other)) return false;
    return id != null && id.equals(other.id);
}

@Override
public int hashCode() {
    return getClass().hashCode();   // constant: stable before and after saving
}

Never put @Data on an entity. It also generates a toString that walks lazy relationships and triggers extra queries or exceptions.

Chapter 23Relationships, and the N+1 problem

Relationships are where JPA is at its most powerful and most treacherous. Read this chapter carefully; it prevents the most common performance disaster in Spring applications.

One-to-many and many-to-one

One user has many orders; each order belongs to one user.

@Entity
public class Order {

    @Id @GeneratedValue private Long id;

    @ManyToOne(fetch = FetchType.LAZY)        // always LAZY here
    @JoinColumn(name = "user_id", nullable = false)
    private User user;                        // this side owns the foreign key
}

@Entity
public class User {

    @Id @GeneratedValue private Long id;

    @OneToMany(mappedBy = "user",             // "Order.user owns this"
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Order> orders = new ArrayList<>();

    public void addOrder(Order order) {       // keep both sides in step
        orders.add(order);
        order.setUser(this);
    }
}

mappedBy marks the non-owning side. The owning side is the one with the foreign key column, and it is the side Hibernate looks at when deciding what to write. Forgetting to set both sides is a classic bug: you add an order to the list, nothing is saved, and nothing warns you.

Many-to-many

@Entity
public class Student {
    @ManyToMany
    @JoinTable(name = "student_course",
               joinColumns = @JoinColumn(name = "student_id"),
               inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();
}
Where people go wrong

Real many-to-many relationships almost always grow extra data — an enrolment date, a grade, a status. @ManyToMany gives you a join table you cannot add columns to. The moment that happens you must restructure everything. Most experienced developers skip @ManyToMany entirely and model the join as its own entity with two @ManyToOne relationships:

@Entity
public class Enrolment {
    @Id @GeneratedValue private Long id;
    @ManyToOne(fetch = LAZY) private Student student;
    @ManyToOne(fetch = LAZY) private Course course;
    private LocalDate enrolledOn;
    private String grade;
}

Eager versus lazy loading

LAZY means the related data is fetched only when you touch it. EAGER means it is fetched immediately, always, in every query that loads the parent.

RelationshipDefaultWhat you should use
@ManyToOneEAGERLAZY — override it
@OneToOneEAGERLAZY — override it
@OneToManyLAZYLAZY, the default is right
@ManyToManyLAZYLAZY, the default is right

The rule is: make everything lazy, then fetch what you need explicitly in the query that needs it. Eager loading is a decision made in the entity, which means it applies to every query everywhere, including the ones that did not want it.

The N+1 problem

This is the single most important performance issue in JPA, so here it is in full.

List<Order> orders = orderRepository.findAll();     // 1 query: SELECT * FROM orders

for (Order order : orders) {
    System.out.println(order.getUser().getName());  // 1 query PER ORDER
}

With 100 orders you have just run 101 queries. Each is fast; together they are catastrophic. At 10,000 orders the page times out. Worse, it does not appear in development with three rows of test data — it appears in production.

Fix one: fetch join

@Query("SELECT o FROM Order o JOIN FETCH o.user")
List<Order> findAllWithUser();          // one query, users included

Fix two: an entity graph

@EntityGraph(attributePaths = {"user", "items"})
List<Order> findByStatus(Status status);

Fix three: batch fetching

spring.jpa.properties.hibernate.default_batch_fetch_size=50

Hibernate then loads related rows in groups of fifty rather than one at a time. This converts 101 queries into 3, and is a good global safety net.

Fix four: ask only for what you need

@Query("SELECT new com.example.OrderSummary(o.id, o.total, u.name) " +
       "FROM Order o JOIN o.user u")
List<OrderSummary> findSummaries();
Where people go wrong

Two related traps:

  • Setting spring.jpa.open-in-view=true. It is on by default and it hides the problem by keeping the database session open while JSON is being written, so lazy loading appears to work in controllers. It also holds a connection for the entire request. Turn it off (spring.jpa.open-in-view=false) and fetch deliberately.
  • Join-fetching two collections at once. JOIN FETCH o.items JOIN FETCH o.payments produces a cartesian product. Fetch one collection per query and use batch fetching for the rest.

Cascade and orphan removal

Cascade typeMeaning
PERSISTSaving the parent saves new children
MERGEUpdating the parent updates children
REMOVEDeleting the parent deletes children
ALLAll of the above

orphanRemoval = true goes further: removing a child from the parent's collection deletes it. Use cascades when the child genuinely cannot exist without the parent — order items belong to an order. Do not cascade from Order to User; deleting an order should not delete the customer.

Worth remembering

Make every relationship LAZY, turn off open-in-view, and fetch explicitly with a join fetch or entity graph. Watch the query log; if the count grows with the number of rows, you have N+1.

Chapter 24Paging, sorting, and dynamic queries

Paging

Returning ten thousand rows in one response is a bug. Page instead.

    Page<Product> findByCategory(String category, Pageable pageable);
}

public Page<ProductResponse> list(
        @RequestParam(defaultValue = "0") int page,

    Pageable pageable = PageRequest.of(page, size, Sort.by(sortBy).descending());

page.getTotalElements()  // total across all pages (costs a COUNT query)
page.getTotalPages()
page.getNumber()         // current page, zero-based
page.hasNext()

If you do not need the total count, return Slice instead — it skips the extra COUNT query and is noticeably faster on large tables.

Where people go wrong

Combining JOIN FETCH on a collection with paging. Hibernate cannot apply LIMIT correctly to a joined collection, so it silently loads every matching row into memory and pages in Java. You will see a warning in the logs about applying pagination in memory. Use an entity graph or batch fetching instead when paging.

Specifications: filters built at run time

A search screen with six optional filters cannot be a method name. Specifications let you compose conditions programmatically.

public interface ProductRepository
        extends JpaRepository<Product, Long>, JpaSpecificationExecutor<Product> { }
public class ProductSpecs {

    public static Specification<Product> hasCategory(String category) {
        return (root, query, cb) ->
            category == null ? null : cb.equal(root.get("category"), category);
    }

    public static Specification<Product> priceAtMost(BigDecimal max) {
        return (root, query, cb) ->
            max == null ? null : cb.lessThanOrEqualTo(root.get("price"), max);
    }

    public static Specification<Product> nameContains(String term) {
        return (root, query, cb) ->
            term == null ? null : cb.like(cb.lower(root.get("name")),
                                          "%" + term.toLowerCase() + "%");
    }
}
Specification<Product> spec = Specification
        .where(ProductSpecs.hasCategory(criteria.category()))
        .and(ProductSpecs.priceAtMost(criteria.maxPrice()))
        .and(ProductSpecs.nameContains(criteria.term()));

Chapter 25Transactions

A transaction is a group of database operations that all succeed or all fail. Transferring money is the standard example: debiting one account and crediting another must never half-happen.

@Service
public class TransferService {

    @Transactional
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepository.findById(fromId).orElseThrow();
        Account to   = accountRepository.findById(toId).orElseThrow();

        from.withdraw(amount);
        to.deposit(amount);
        // if anything throws here, BOTH changes are undone
    }
}

Where to put @Transactional

On service methods. That is the layer where a unit of business work is defined. Repositories already have their own transaction for single operations, and controllers should not know about transactions at all.

Read-only transactions

@Service
@Transactional(readOnly = true)          // the default for this class
public class ProductService {

    public List<Product> findAll() { ... }      // read-only, cheaper

    @Transactional                               // overridden for writes
    public Product create(CreateProductRequest request) { ... }
}

readOnly = true lets Hibernate skip dirty checking and lets some databases route the query to a replica. It is a genuine optimisation, not just documentation.

Rollback rules, and the trap inside them

Where people go wrong

By default, Spring rolls back for RuntimeException and Error, but commits for checked exceptions. This surprises almost everyone:

@Transactional
public void process() throws IOException {
    repository.save(entity);
    throw new IOException("failed");     // the save IS COMMITTED
}

Either use unchecked exceptions, or say so explicitly:

@Transactional(rollbackFor = Exception.class)

A second, even more common trap: catching an exception inside the transactional method and swallowing it means Spring never sees a failure and commits happily. If you catch, either rethrow or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().

Propagation: what happens when one transactional method calls another

PropagationBehaviour
REQUIREDJoin the existing transaction, or start one. The default, and right nearly always.
REQUIRES_NEWAlways start a separate transaction, suspending the current one. Use for audit logs that must survive a rollback.
SUPPORTSJoin if one exists, otherwise run without.
NOT_SUPPORTEDSuspend any transaction and run without one.
MANDATORYFail if there is no existing transaction.
NEVERFail if there is one.
NESTEDA savepoint inside the current transaction.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAuditRecord(String action) {
    // committed even if the calling transaction rolls back
}

The self-invocation trap, again

Where people go wrong

@Transactional uses the same proxy mechanism as AOP, so it has the same blind spot:

@Service
public class OrderService {

    public void processAll(List<Order> orders) {
        orders.forEach(this::processOne);   // NO transaction — internal call
    }

    @Transactional
    public void processOne(Order order) { ... }
}

Move processOne to a separate bean and inject it. This trap accounts for a startling share of "my transaction is not working" bug reports.

Isolation and concurrent updates

Isolation controls how much one transaction can see of another's uncommitted work. The defaults from your database are almost always correct, so change them only with a specific reason.

What you will need is protection against two users editing the same row. Optimistic locking is the usual answer:

@Entity
public class Product {
    @Version
    private Long version;      // Hibernate increments this on every update
}

If two users load version 3 and both save, the first succeeds and bumps it to 4; the second fails with OptimisticLockingFailureException, which you translate into a 409 Conflict. No locks are held, and no update is silently lost.

Worth remembering

@Transactional on service methods, readOnly = true for queries, remember that checked exceptions do not roll back by default, and never rely on it for a call inside the same class.

Letting Hibernate alter your production schema is a bad idea: the changes are invisible, unreviewable, and irreversible. Flyway makes every schema change an ordinary, version-controlled file.

Editing a migration file that has already run. Flyway stores a checksum; changing an applied file makes startup fail. This is correct behaviour — the file already ran elsewhere and editing it would mean two environments silently diverge. Always add a new migration instead.

Chapter 27Spring Security fundamentals

Security answers two separate questions, and keeping them separate makes the whole subject easier.

  • Authentication: who are you? Proved by a password, a token, or a certificate.
  • Authorisation: now that I know who you are, what are you allowed to do?

What happens when you add the starter

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Restart and every endpoint is protected, a login form appears, and a generated password is printed in the console. That default exists to make the safe state the easy state. You now configure it deliberately.

The filter chain

Spring Security is a chain of servlet filters that runs before the DispatcherServlet. Each filter has one job: read the login form, check the token, load the user, decide access. Understanding that it is a chain explains why security decisions happen before your controller is ever selected.

Configuring it

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())            // see the note below
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**", "/api/public/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers("/api/orders/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()        // always end with this
            )
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .httpBasic(Customizer.withDefaults())
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

Where people go wrong

Order matters and it is first-match-wins. If anyRequest().authenticated() appears before your permitAll() rules, the specific rules never run. Put the most specific patterns first and the catch-all last.

On CSRF: disabling it is correct for a stateless API authenticated by a token in a header, because the attack it prevents relies on the browser automatically attaching a cookie. If you use cookie-based sessions with a browser front-end, leave CSRF protection enabled.

Passwords

Store a hash, never the password, and never a plain hash like MD5 or SHA-256 — those are designed to be fast, which is exactly wrong here. BCrypt is deliberately slow and salts each hash automatically.

String hash = passwordEncoder.encode(rawPassword);           // on registration
boolean ok = passwordEncoder.matches(rawPassword, hash);     // on login

Chapter 28Token-based authentication with JWT

Sessions store user state on the server, which means every request must reach the same server or a shared session store. A JSON Web Token moves that state to the client: the server signs a token, the client sends it back, and the server verifies the signature without looking anything up.

What a token contains

Three base64 segments separated by dots: a header saying which algorithm signed it, a payload of claims (who the user is, when it expires), and a signature over the first two.

Where people go wrong

The payload is encoded, not encrypted. Anyone holding the token can read every claim in it. Never put anything confidential in a JWT. The signature guarantees the claims have not been altered; it guarantees nothing about privacy.

The flow

  1. The client posts credentials to /api/auth/login.
  2. The server checks them and returns a signed token.
  3. The client sends Authorization: Bearer <token> on every later request.
  4. A filter validates the signature and expiry, and populates the security context.

Creating and reading tokens

@Service
public class JwtService {

    private final SecretKey key;
    private final long expiryMinutes;

    public JwtService(@Value("${app.jwt.secret}") String secret,
                      @Value("${app.jwt.expiration-minutes}") long expiryMinutes) {
        this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        this.expiryMinutes = expiryMinutes;
    }

    public String generate(UserDetails user) {
        Instant now = Instant.now();
        return Jwts.builder()
                .subject(user.getUsername())
                .claim("roles", user.getAuthorities().stream()
                        .map(GrantedAuthority::getAuthority).toList())
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(expiryMinutes, ChronoUnit.MINUTES)))
                .signWith(key)
                .compact();
    }

    public String extractUsername(String token) {
        return parse(token).getSubject();
    }

    public boolean isValid(String token, UserDetails user) {
        try {
            Claims claims = parse(token);
            return claims.getSubject().equals(user.getUsername())
                   && claims.getExpiration().after(new Date());
        } catch (JwtException e) {
            return false;     // bad signature, malformed, or expired
        }
    }

    private Claims parse(String token) {
        return Jwts.parser().verifyWith(key).build()
                   .parseSignedClaims(token).getPayload();
    }
}

The filter

@Component
public class JwtAuthFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    public JwtAuthFilter(JwtService jwtService, UserDetailsService userDetailsService) {
        this.jwtService = jwtService;
        this.userDetailsService = userDetailsService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {

        String header = request.getHeader("Authorization");
        if (header == null || !header.startsWith("Bearer ")) {
            chain.doFilter(request, response);
            return;
        }

        String token = header.substring(7);
        String username = jwtService.extractUsername(token);

        if (username != null &&
            SecurityContextHolder.getContext().getAuthentication() == null) {

            UserDetails user = userDetailsService.loadUserByUsername(username);
            if (jwtService.isValid(token, user)) {
                var auth = new UsernamePasswordAuthenticationToken(
                        user, null, user.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                SecurityContextHolder.getContext().setAuthentication(auth);
            }
        }
        chain.doFilter(request, response);
    }
}

Wiring it into the chain

        throws Exception {
    return http

        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth

The login endpoint

@RestController

    private final AuthenticationManager authManager;
    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    @PostMapping("/login")
    public TokenResponse login(@Valid @RequestBody LoginRequest request) {

Practical cautions

  • A token cannot be revoked. Once signed, it is valid until it expires. Keep access tokens short-lived — fifteen minutes is typical — and issue a longer-lived refresh token that is stored server-side and can be deleted.
  • The secret must be long and random, at least 256 bits for HS256, and must come from the environment. A short or committed secret makes the whole scheme worthless.
  • Always use HTTPS. A token sent over plain HTTP is a password in the clear.
  • Prefer an existing identity provider — Keycloak, Auth0, Cognito — for anything handling real user accounts. Rolling your own authentication is a solved problem you can get subtly wrong.
Worth remembering

A JWT is signed, not secret. Keep it short-lived, keep the signing key in the environment, and use a refresh token when you need the ability to revoke access.

Chapter 30Caching

If a result is expensive to produce and does not change often, computing it once and reusing it is the cheapest performance win available.

@SpringBootApplication
@EnableCaching
public class ShopApplication { }
@Service
public class ProductService {

    @Cacheable(value = "products", key = "#id")
    public Product findById(Long id) {
        return repository.findById(id).orElseThrow();   // runs only on a miss
    }

    @CachePut(value = "products", key = "#product.id")
    public Product update(Product product) {
        return repository.save(product);                // always runs, then caches
    }

    @CacheEvict(value = "products", key = "#id")
    public void delete(Long id) {
        repository.deleteById(id);
    }

    @CacheEvict(value = "products", allEntries = true)
    public void reloadCatalogue() { }

    @Cacheable(value = "products", key = "#category", condition = "#category != null",
               unless = "#result.isEmpty()")
    public List<Product> findByCategory(String category) { ... }
}

condition is checked before the method runs and decides whether to consult the cache at all. unless is checked after, against the result, and decides whether to store it. Empty results are usually not worth caching.

Where people go wrong

Three traps:

  • No expiry. The default in-memory cache grows until the process runs out of memory. Always set a size or time limit.
  • Stale data. If anything else writes to the table, your cache is wrong and will stay wrong. Cache things that are read far more often than written, and evict on every write path.
  • Self-invocation. Caching is proxy-based, so a method calling a @Cacheable method inside the same class gets no caching. The same rule as @Transactional and AOP.
Worth remembering

Cache what is read often and written rarely, always set an expiry, and evict whenever the underlying data changes.

Scheduled tasks

@SpringBootApplication

public class ShopApplication { }

    public void pollQueue() { }

    public void syncInventory() { }

Cron fields in Spring are: second, minute, hour, day of month, month, day of week. Note the leading seconds field — it differs from Unix cron and catches people out.

Where people go wrong

Two issues bite in production:

  • One thread by default. All scheduled tasks share a single thread, so a slow job delays every other job. Configure a pool: spring.task.scheduling.pool.size=5.
  • Every instance runs it. Deploy three copies of your application and the nightly cleanup runs three times. Use ShedLock or a database lock to make sure only one instance executes.

Define your own executor

The default executor is unbounded, which means a burst of work can create an unlimited number of threads.

@Bean(name = "taskExecutor")
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(4);
    executor.setMaxPoolSize(16);
    executor.setQueueCapacity(100);
    executor.setThreadNamePrefix("async-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.initialize();
    return executor;
}
Where people go wrong

@Async is proxy-based too, so calling an async method from within the same class runs it synchronously. Also, an exception thrown from a void async method disappears entirely unless you register an AsyncUncaughtExceptionHandler. And the security context and any open transaction do not carry over to the new thread by default.

Worth remembering

Configure a bounded pool for both scheduling and async work, guard scheduled jobs against running on every instance, and remember the same-class proxy limitation.

Chapter 33Microservices with Spring Cloud

Where people go wrong

Reaching for microservices too early. Splitting an application into services converts simple method calls into network calls that can fail, turns one transaction into a distributed coordination problem, and multiplies your deployment and monitoring work. Start with a well-organised single application — a modular monolith — and split only when you have a concrete reason: independent scaling, independent release cycles, or independent teams. "It is what modern companies do" is not a reason.

The problems that appear once you split

  1. How does service A find service B's address? Service discovery.
  2. How do clients reach twenty services? An API gateway.
  3. How do twenty services share configuration? A config server.
  4. What happens when B is down? Circuit breakers.
  5. How do you trace one user action across six services? Distributed tracing.

Spring Cloud is a set of answers to those five questions.

Resilience with circuit breakers

If a downstream service is failing, continuing to call it wastes threads and makes your service fail too. A circuit breaker notices the failure rate, stops calling for a while, and periodically tests whether the service has recovered.

@Service
public class ProductService {

    @CircuitBreaker(name = "productService", fallbackMethod = "cachedProduct")
    @Retry(name = "productService")
    @TimeLimiter(name = "productService")
    public ProductResponse find(Long id) {
        return productClient.findById(id);
    }

    private ProductResponse cachedProduct(Long id, Throwable cause) {
        log.warn("product-service unavailable, serving cached copy", cause);
        return cache.get(id);
    }
}
resilience4j:
  circuitbreaker:
    instances:
      productService:
        sliding-window-size: 20
        failure-rate-threshold: 50        # open after 50% of 20 calls fail
        wait-duration-in-open-state: 30s
        permitted-number-of-calls-in-half-open-state: 3

The breaker has three states: closed (calls pass through), open (calls fail immediately and the fallback runs), and half-open (a few test calls decide whether to close again).

Distributed tracing

Add Micrometer Tracing with an exporter such as Zipkin, and every request gets a trace id that is passed along to each service it touches. You can then see one user action as a single timeline across six applications, which is the only practical way to debug a distributed system.

Worth remembering

Microservices trade simplicity for independence. Take that trade only when you need the independence, and when you do, you will need discovery, a gateway, shared configuration, circuit breakers, and tracing from the start.

Chapter 34Messaging

A direct HTTP call couples two services in time: both must be up at the same moment. A message broker removes that coupling. The sender publishes and moves on; the receiver processes when it can.

When to use messaging

  • The work can happen later — sending emails, generating reports, updating search indexes.
  • Several systems care about the same event and you do not want the publisher to know them all.
  • Traffic is spiky and you want a queue to absorb the peak.
  • The receiver may be temporarily down and you cannot lose the work.

Assuming a message arrives exactly once. Under failure, brokers redeliver, so your consumer will sometimes see the same message twice. Chapter 36Performance and good practice

The performance problems that actually occur

In practice, slow Spring applications are slow for a short list of reasons. Work down this list before reaching for anything exotic.

  1. N+1 queries. By a wide margin the most common. Chapter 23.
  2. Fetching more data than needed. No paging, no projections, SELECT * on wide tables.
  3. Missing indexes. Any column you filter or join on should almost certainly have one.
  4. Eager loading everywhere. One entity drags half the database into memory.
  5. Calls without timeouts. One slow dependency exhausts your thread pool.
  6. A connection pool too small or too large. Too small queues requests; too large overwhelms the database.

Measure before changing anything

# see every query and its parameters
spring.jpa.show-sql=true
logging.level.org.hibernate.orm.jdbc.bind=TRACE

# count queries per request and warn on slow ones
decorator.datasource.datasource-proxy.slow-query.threshold=1

Then use Actuator metrics and a profiler. Optimising code you have not measured is guessing, and the guess is usually wrong.

Practices worth adopting

Design

  • Constructor injection, final fields, no field injection.
  • Interfaces where a substitution is plausible; concrete classes where it is not. Do not create an interface with exactly one implementation just to have one.
  • Package by feature, not by layer.
  • Keep classes small. A service with fifteen dependencies is several services.
  • Prefer immutable objects: records for DTOs, final fields, no setters unless mutation is genuinely part of the model.

Data

  • Everything lazy; fetch explicitly with a join fetch or entity graph.
  • open-in-view=false.
  • Page every list endpoint.
  • @Transactional(readOnly = true) for reads.
  • Flyway for schema, validate for Hibernate.
  • Use BigDecimal for money, never double.

API

  • Version from the first release.
  • Never expose entities; always DTOs.
  • Consistent error shape from one @RestControllerAdvice.
  • Validate everything that comes from outside.
  • Honest status codes.

Security

  • Secrets from the environment.
  • BCrypt for passwords.
  • HTTPS everywhere.
  • Never log credentials, tokens, or personal data.
  • Keep dependencies current; run ./mvnw versions:display-dependency-updates and a vulnerability scanner.

Questions to check your understanding

Answer each in your own words before reading the response. If an answer surprises you, reread that chapter.

What is a bean?

Any object created and managed by the Spring container, either from a scanned @Component or from an @Bean method.

Why is constructor injection preferred over field injection?

Fields can be final, the object can never exist half-built, dependencies are visible in the signature, and the class can be constructed in a test without Spring.

What is the default bean scope, and what does it oblige you to do?

Singleton — one instance shared by everything. Because it is shared across threads, it must not hold mutable state in fields.

How does auto-configuration work?

Spring Boot ships conditional configuration classes. Each is guarded by conditions such as "this class is on the classpath" and "the user has not defined this bean." Only those whose conditions pass contribute beans.

Why does @Transactional sometimes do nothing?

Because it works through a proxy. A call from one method to another inside the same class never passes through the proxy, so the annotation is skipped. Private methods are never intercepted either.

What is the N+1 problem?

One query fetches N rows, then touching a lazy relationship on each triggers one more query per row. Fix it with a fetch join, an entity graph, or batch fetching.

Why should you never return entities from a controller?

They expose internal and sensitive fields, cause lazy-loading failures during JSON serialisation, tie your API contract to your schema, and can recurse infinitely.

Do checked exceptions roll back a transaction?

No. By default only unchecked exceptions and errors trigger a rollback. Use rollbackFor = Exception.class if you need otherwise.

What is the difference between @NotNull, @NotEmpty and @NotBlank?

Null check; null plus size check; null plus at least one non-whitespace character. For strings you almost always want @NotBlank.

Is a JWT encrypted?

No. It is signed and base64-encoded. Anyone holding it can read the claims. The signature prevents tampering, not reading.

What does @SpringBootApplication combine?

@SpringBootConfiguration, @EnableAutoConfiguration, and @ComponentScan of its own package downwards.

When should you choose microservices?

When you need independent scaling, independent deployment, or independent team ownership — and are willing to pay for network failure handling, distributed tracing, and much harder transactions.
